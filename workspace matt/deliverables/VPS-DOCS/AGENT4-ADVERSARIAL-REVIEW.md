## F-C1 [MED] — Daftar node MVP "dari frekuensi penggunaan" ditulis tanpa data; sekarang datanya ada, wajib dipakai
PRD-2 §7.3 mengklaim Tier 1-3 "diturunkan dari node yang paling sering muncul di workflow nyata — bukan dari daftar n8n", tapi pada saat dokumen ditulis belum ada satu pun workflow nyata di tangan. Sekarang korpus 96 template nyata sudah terkumpul (40 agent1 + 56 agent4) + fixtures. **Serangan:** tanpa pengukuran, §7.3 adalah tebakan terpelajar — persis yang dilarang ZERO ASSUMPTION. **Tindakan:** sebelum Fase 1 node-writing, jalankan coverage scan korpus → hitung distribusi `node.type` di 96 file → validasi: apakah 13 node Tier 1 cukup untuk ≥X% file; apakah ada node di luar Tier 1-3 yang frekuensinya tinggi (mis. spreadsheetFile muncul di banyak template era awal). Output: revisi tabel §7.3 berbasis angka + laporan korban (file mana yang gagal impor karena node tak didukung). Wawasan: file saya sendiri menunjukkan template publik awal n8n didominasi `readBinaryFile`/`writeBinaryFile`/`spreadsheetFile`/`postgres` — tiga pertama tidak ada di Tier 1 maupun Tier 2. Kemungkinan revisi nyata.

## F-C2 [HIGH] — Codegen OpenAPI: tidak ada pemetaan eksplisit tipe parameter OpenAPI → ParameterSchema, dan tidak ada default SideEffect berbasis metode HTTP
PRD-2 §7.4 membahas kualitas spec publik (R8) tapi tidak mendefinisikan: (1) transformasi tipe skema OpenAPI (string/number/integer/boolean/array/enum/oneOf/anyOf) ke tipe ParameterSchema — padahal spec penuh `oneOf`/`anyOf`/nullable akan sering muncul; (2) aturan serialisasi array di query (`style=form/spaceDelimited/pipeDelimited`), (3) pagination & rate limit. **Serangan paling tajam:** generator tidak mungkin tahu idempotensi endpoint, tapi ResourceHint.SideEffect (PRD-2 §7.2) adalah kunci keputusan recovery (InDoubt vs retry aman). Tanpa default eksplisit, generated node entah semua jadi `NonIdempotent` (recovery selalu NEEDS_REVIEW → gate Fase 1 "Node NonIdempotent crash → InDoubt teruji" jadi alarm palsu massal) atau semua `Idempotent` (bahaya duplikasi POST). **Usul:** default berbasis metode HTTP: GET/HEAD/OPTIONS → `Idempotent`; PUT/DELETE → `Idempotent` (syarat: path parameter lengkap — verifikasi per spec); POST/PATCH → `NonIdempotent`; + mekanisme override manual per node hasil generate (file `verifications/<node>.json`), + rejection rules utk pola spec yang tidak bisa dipetakan (harus gagal build, bukan hasilkan node rusak).

## F-C3 [HIGH] — `typeVersion` tidak diperlakukan sebagai dimensi skema: workflow lama akan divalidasi terhadap skema node terbaru
PRD-1 §4.2: tiap node di workflow mem-pin `typeVersion`; PRD-2 NodeDescriptor punya `version`, tapi tidak ada aturan registry skema **per (kind, typeVersion)** di alur impor/validasi. Node n8n berubah antar versi (httpRequest v1 vs v4.x punya parameter berbeda; readBinaryFile, spreadsheetFile era awal typeVersion 1). **Serangan:** parser L1 yang me-resolve parameter terhadap skema versi terbaru akan (a) menolak/menandai workflow lama yang sah, atau lebih buruk (b) menerima tapi salah interpretasi field lama → deviasi diam-diam (silent). Korpus 96 template era 2019-2026 akan menabrak ini pada hari pertama differential testing. **Usul:** schema registry `(kind, typeVersion) → ParameterSchema`; kebijakan impor: versi eksplisit = validasi terhadap skema versi itu (tanpa migrasi); versi hilang/0 = fallback skema tertua yang dikenal + catat deviasi; migrasi antar-versi HANYA via mapping eksplisit di katalog deviasi, tidak otomatis. Ini juga menyederhanakan spec schema-compiler saya: kompilasi per (kind,typeVersion), bukan per kind.

## F-C4 [MED] — Kontrak evaluasi parameter per-item vs per-task tidak dinyatakan → risiko deviasi L3
PRD-2 §6.2 langkah c: "Resolusi parameter → eval expression via QuickJS" (per Task), sedangkan PRD-1 §8.1/§8.5: expression dievaluasi **per item** dan `$json`/`$itemIndex` berbeda tiap item. NodeDescriptor.params statis per node. **Serangan:** tanpa kontrak eksplisit field mana yang dievaluasi per-item vs sekali-per-task (mis. `executeOnce`, credential resolution, header statis vs body per item), dua implementasi engine akan berbeda output untuk workflow yang sama — dan differential test baru menangkapnya setelah berbulan-bulan. **Usul:** di kernel spec: setiap `ParameterSchema` diberi atribut evaluasi (per-item default untuk nilai yang menyentuh `$json/$itemIndex/$input`; sekali-per-task untuk `$execution/$workflow/$now` yang dibekukan saat task start — atau justru sebaliknya: n8n mengevaluasi per-item hampir selalu, kunci: **per-item** default + pengecualian eksplisit `executeOnce`/node-level). Tetapkan di Fase 1 bersama executor, dan jadikan kasus uji differential wajib (workflow 1 Set + expression $json + $itemIndex).

## F-C5 [MED] — Codegen B & kredensial: tidak ada kontrak token refresh untuk node hasil generate
PRD-1 §7.5: OAuth2 adalah bagian termahal integrasi; PRD-2 §11: least privilege via `NodeDescriptor.credentials`, CredentialValue redaction. Tapi §7.4 (codegen) tidak menyebut bagaimana node hasil generate menangani auth — apakah memakai credential type deklaratif (`authenticate.generic`), atau harus mengimplementasikan refresh token sendiri. Kalau tiap generated node menyimpan/menyegarkan token sendiri, dua prinsip §11 (scoping & redaction) bocor. **Usul:** putuskan di Fase 2 sebelum prototipe codegen: GeneratedNode WAJIB memakai kredensial via `NodeDescriptor.credentials` + service refresh per-tipe di crate `auth` (trait di kernel: `CredentialRefresher`), dilarang menyimpan token di luar credential store. Node hasil generate yang spec-nya butuh OAuth2 tanpa definisi credential type → masuk daftar "perlu kurasi manual", bukan otomatis.

## F-C6 [MED] — PriorOutputs & spill: governor butuh komponen budget & metrik hit/miss yang belum ada
PRD-2 §8.2: `$('Node')` membaca output node lain "dari spill"; §5.1: spill file di-GC saat execution terminal. Selama eksekusi, akses acak ke output node mana pun harus tetap mungkin — artinya perlu index `(node_id, runIndex, item_range)` ke spill + cache LRU. §6.4 Memory Governor mengatur inline vs spill list, **tapi tidak menghitung budget "prior outputs cache"** — padahal justru ini yang bisa membengkak tak terkendali di workflow besar (N node × output besar, semua harus addressable). Metrik M3 mengukur overhead spill vs inline tapi tidak mengukur hit/miss prior-output. **Usul:** tambah ke spec data-plane: struktur index prior-output + batas cache (mis. X% budget governor) + metrik `prior_output_hit_ratio`; kasus uji: workflow 10 node, node ke-10 membaca output node ke-1 yang sudah ter-spill (wajib lolos tanpa reload seluruh file).
